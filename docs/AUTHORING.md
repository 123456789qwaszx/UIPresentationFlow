# 화면 제작 원칙 — 명세가 원본, 프리팹은 산출물

화면 스크립트와 **빌드 명세**를 쓰면, 빌더가 그 프로젝트의 Unity로 프리팹을 만든다. 사람은 Unity에서 결과를 보고 판정한다. AI도 사람도 프리팹의 직렬화 데이터(YAML)를 손으로 쓰지 않는다.

이 원칙은 [ked-presentation-runtime](#참고-구현)의 비주얼 노벨 예제 UI 12화면(Root 2 · Panel 6 · Page 4)을 이 프레임워크 위에 다시 세우면서 정했다(2026-10-27). 거기서 AI가 화면 스크립트와 명세를 쓰고, 개발자가 Unity에서 빌드해 검수하는 흐름이 실제로 돌았다.

## 왜 프리팹을 직접 쓰지 않나

AI가 Unity 밖에서 프리팹을 만든다는 것은 YAML을 손으로 쓴다는 뜻이다.

| | 프리팹을 직접 쓴다 | 명세를 쓰고 빌더가 짓는다 |
|---|---|---|
| 확인 | fileID · 컴포넌트 칸 · RectTransform · TMP 내부 값이 어긋나면 Unity를 열어야 드러난다 | 명세는 C# 컴파일로 거른다. 노드 이름을 `nameof(MyScreen.Refs.X)`로 쓰면 화면의 Refs와 어긋날 때 컴파일이 깨진다 |
| Unity 버전 | 직렬화 형식이 버전마다 다르다. 어느 버전 기준인지부터 불안하다 | 그 프로젝트의 Unity가 저장하니 그 버전에서 항상 올바르다 |
| 리뷰 | 프리팹 diff는 사람이 읽기 어렵다 | 명세 diff가 곧 "무엇을 바꿨나"다 |
| 재생성 | — | 같은 명세면 같은 결과(아래 "재생성") |

## 원본과 산출물

| 구분 | 무엇 | 규칙 |
|---|---|---|
| 원본 | 화면 스크립트 · 빌드 명세 · 그림 · 부품 키트 | 고칠 것은 여기서 고친다 |
| 산출물 | 화면 프리팹 · 화면을 모은 캔버스 · 빌더가 만든 글꼴 자산 | 빌드마다 덮어쓴다. **손으로 고치지 않는다** — 다음 빌드에서 사라진다. 클론만으로 실행되게 **커밋한다** |
| 처음 한 번 만드는 데이터 | Presentation(`UIPresentationSpec`) · 화면에 맞춘 데이터 | 없을 때만 빌더가 만든다. 그 뒤로는 에셋에서 고친다(빌더가 덮지 않는다) |

생성한 에셋은 **오브젝트 이름 = 파일 이름**으로 둔다. 파일 이름만 바꾸면 Unity가 "main object name should match the asset filename" 경고를 낸다. 프레임워크는 Presentation을 오브젝트 이름이 아니라 `presentationId`로 찾으므로 이름을 맞춰도 동작은 같다.

## 화면 묶음

화면 하나를 묶음 하나로 둔다 — 그 화면의 코드 · 프리팹 · 그림 · Presentation이 한 폴더에 있다.

```text
<UI 뿌리>/
├─ <런타임 asmdef>             뿌리에 둔다(Common · Screens · 앱 코드를 덮는다)
├─ Common/                      여러 화면이 같이 쓰는 것 — 어느 화면도 이름으로 알지 않는다
│   ├─ Scripts/                 부품 키트(버튼 · 슬라이더 …)
│   ├─ Editor/                  키트로 짓는 도구 · 묶음 규칙 · 검사 + 에디터 asmdef
│   ├─ Sprites/                 둘 이상의 화면이 쓰는 그림
│   └─ Fonts/
├─ Screens/<묶음>/
│   ├─ Scripts/                 화면 · 위젯 스크립트(UIBase<TRefs>)
│   ├─ Prefabs/                 산출물
│   ├─ Presentation/            <화면>Presentation.asset
│   ├─ Sprites/                 그 화면만 쓰는 그림(없으면 폴더도 없다)
│   └─ Editor/                  빌드 명세 + 에디터 asmdef를 가리키는 .asmref
├─ <앱 코드>/                   화면 흐름 · 호스트(어느 화면을 언제 여는지)
└─ <앱 빌드>/                   화면 목록 · 캔버스를 짓는 빌드 + .asmref
```

- Page는 주인 Panel의 묶음에 둔다. 명세 하나가 여러 화면을 만들면(확인 · 안내 창) 한 묶음에 둔다.
- 화면 흐름, 앱 설정 값, 화면을 모은 캔버스, 글자 표(CSV 하나)는 묶음에 넣지 않는다. 화면을 쓰는 앱의 몫이다.
- **asmdef 아래의 `Editor` 폴더는 에디터 전용이 아니다.** 런타임 asmdef가 뿌리에 있으면 묶음 안의 `Editor/`도 그 아래라, `.asmref`로 에디터 asmdef에 붙여야 한다. 실행 쪽과 짝이 맞는다: `Common/Scripts` ↔ `Common/Editor`, 앱 코드 ↔ 앱 빌드, `Screens/X/Scripts` ↔ `Screens/X/Editor`.
- 그림은 경로가 아니라 이름으로 찾게 하면, 공용과 화면 전용 사이를 옮겨도 명세를 고치지 않는다. 같은 이름은 둘 두지 않는다.

## 특수 화면 — 프리팹을 직접 만들 때

비정형 배치나 복잡한 연출처럼 명세로 나타내기 어려운 화면은, 프리팹을 손이나 에디터 스크립트로 직접 만들어도 된다. 조건은 셋이다.

1. 같은 `UIBase<TRefs>`를 쓴다. 게임과 잇는 방식은 하나로 남는다.
2. 묶음 구조를 따른다.
3. 같은 검사를 지난다.

모든 화면을 명세로 덮으려고 명세를 넓히지 않는다. 데이터로 화면을 조립하던 구조에서 프리팹 중심으로 돌아온 까닭이 그것이다. 명세를 넓힐지, 공용으로 올릴지는 사람이 정한다.

## 검사

빌드와 따로 돌 수 있어야 한다. 그래야 손으로 만든 프리팹도 같은 그물을 지난다.

- **Refs** — 화면 · 위젯마다 `Refs`의 이름이 제 아래에 정확히 하나 있다(`UIBase`는 이름으로 첫 번째를 잡는다).
- **Presentation** — 오브젝트 이름이 파일 이름과 같고, `presentationId`가 비지 않았다.
- **그림 이름** — 같은 이름이 둘 없다.
- **묶음이 닫혀 있다** — 묶음 안의 에셋이 가리키는 것이 제 묶음 · Common · 이 프레임워크 · 게임 쪽 프레임워크 · Unity 패키지뿐이다. 다른 화면 묶음을 가리키지 않는다.

배치 모드 진입점(`-executeMethod`)을 두면 사람이 메뉴를 누르지 않아도 빌드 · 검사를 돌릴 수 있다. Unity가 그 프로젝트를 열고 있으면 배치 모드는 프로젝트를 열지 못한다.

## 배포(반입) — 두 방식

묶음은 원본과 산출물(`.meta` 포함)을 함께 담는다.

| 받는 쪽 | 방법 |
|---|---|
| Unity 버전 · 패키지가 같다 | 산출물째 들인다 — 검수한 그대로, GUID 그대로 |
| 다르다 | 원본과 산출물의 `.meta`를 들이고 그 자리 위에 다시 빌드한다 — 직렬화 형식 문제를 피하고 GUID는 지킨다 |

다시 빌드할 때 파일 안쪽 fileID가 Unity 버전을 넘어 그대로인지는 아직 확인하지 않았다.

## 재생성

같은 명세로 다시 빌드하면 산출물이 같다. ked에서 여러 번 빌드한 뒤 묶음의 프리팹 13개(화면 12 · 선택지 항목 1)와 캔버스의 git 변경이 0이었고, Unity가 같은 내용이라 파일을 다시 쓰지도 않았다(2026-10-27, 같은 PC · 같은 버전).

## 사람의 역할

1. **만들기 전** — 요구와 품질 기준을 정한다(무엇을 보여 주나, 어떤 입력 · 해상도 · 언어를 견디나).
2. **만드는 동안** — AI의 설계 판단을 정한다: 명세를 넓힐지, 공용으로 올릴지, 특수 화면으로 뺄지.
3. **만든 뒤** — Unity에서 눈으로 검수하고 승인한다(보기 · 조작 · 화면비 · 다국어 · 실제 흐름). 문제를 찾으면 프리팹이 아니라 원본을 고쳐 다시 빌드한다.

자동 검사는 참조와 구조를 거른다. 화면이 보기 좋은지, 조작하기 편한지, 의도한 분위기인지는 사람이 판정한다.
