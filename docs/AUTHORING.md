# 화면 제작 원칙 — 명세가 원본, 프리팹은 산출물

화면 스크립트와 **빌드 명세**를 쓰면, 빌더가 그 프로젝트의 Unity로 프리팹을 만든다. 사람은 Unity에서 결과를 보고 판정한다. AI도 사람도 프리팹의 직렬화 데이터(YAML)를 손으로 쓰지 않는다.

이 원칙은 [ked-presentation-runtime](#참고-구현)의 비주얼 노벨 예제 UI 12화면(Root 2 · Panel 6 · Page 4)을 이 프레임워크 위에 다시 세우면서 정했다(2026-10-27). 거기서 AI가 화면 스크립트와 명세를 쓰고, 개발자가 Unity에서 빌드해 검수하는 흐름이 실제로 돌았다.

## 왜 프리팹을 직접 쓰지 않나

AI가 Unity 밖에서 프리팹을 만든다는 것은 YAML을 손으로 쓴다는 뜻이다.

| | 프리팹을 직접 쓴다 | 명세를 쓰고 빌더가 짓는다 |
|---|---|---|
| 확인 | fileID · 컴포넌트 칸 · RectTransform · TMP 내부 값이 어긋나면 Unity를 열어야 드러난다 | 명세는 C# 컴파일로 거른다. 노드 이름을 `nameof(MyScreen.Refs.X)`로 쓰면 화면의 Refs와 어긋날 때 컴파일이 깨진다 |
| Unity 버전 | 직렬화 형식이 버전마다 다르다. 어느 버전 기준인지부터 불안하다 | 그 프로젝트의 Unity가 저장하니 그 버전에서 항상 올바르다 |
| 리뷰 | 프리팹 diff는 사람이 읽기 어렵다 | 명세 diff가 곧 "무엇을 바꿨나"다 |
| 재생성 | — | 같은 명세면 같은 결과(아래 "재생성") |

## 원본과 산출물

| 구분 | 무엇 | 규칙 |
|---|---|---|
| 원본 | 화면 스크립트 · 빌드 명세 · 그림 · 부품 키트 | 고칠 것은 여기서 고친다 |
| 산출물 | 화면 프리팹 · 화면을 모은 캔버스 · 빌더가 만든 글꼴 자산 | 빌드마다 덮어쓴다. **손으로 고치지 않는다** — 다음 빌드에서 사라진다. 클론만으로 실행되게 **커밋한다** |
| 처음 한 번 만드는 데이터 | Presentation(`UIPresentationSpec`) · 화면에 맞춘 데이터 | 없을 때만 빌더가 만든다. 그 뒤로는 에셋에서 고친다(빌더가 덮지 않는다) |

생성한 에셋은 **오브젝트 이름 = 파일 이름**으로 둔다. 파일 이름만 바꾸면 Unity가 "main object name should match the asset filename" 경고를 낸다. 프레임워크는 Presentation을 오브젝트 이름이 아니라 `presentationId`로 찾으므로 이름을 맞춰도 동작은 같다.

**플레이 중에는 짓지 않는다.** 플레이 중에 만든 오브젝트는 Awake가 돌아서, 실행 중에만 붙는 것(버튼 연출이 붙이는 `UI_EventHandler` 등)이 섞인 채 저장된다. ked에서 이전 빌드가 그렇게 저장된 것을 편집 모드로 다시 지으며 알았다. `UIPrefabs.CanBuild`가 막는다.

## 도구 — 누가 무엇을 맡나

| 맡는 쪽 | 무엇 | 어디 |
|---|---|---|
| 이 프레임워크 | 시안 좌표 → 앵커(`UINodes`), 저장 · 플레이 중 거부(`UIPrefabs`), Presentation 한 번 만들기(`UIPresentationAssets`), 그림을 이름으로(`UISpriteIndex`), 화면 묶음 규칙 · 감사(`UIScreenUnits`), 검사(`UIScreenValidation`), 동적 글꼴(`UIFontAssets`) | `Editor/UI/Authoring` (에디터 asmdef `UIPresentationFlow.Editor`) |
| 게임의 부품 키트 | 그림 · 글꼴 · 색 · 버튼 꼴 — `TextButton`, `IconButton`, 슬라이더 … | 게임의 `Common/Editor` |
| 화면의 빌드 명세 | 그 화면의 노드와 시안 숫자 — 키트로 짓는다 | `Screens/<묶음>/Editor` |
| 앱 빌드 | 화면 목록과 순서(Page 다음 그 주인, 항목 다음 캔버스), 캔버스, 앱 데이터, 메뉴 | 게임의 앱 빌드 |

명세를 프레임워크가 스스로 찾지 않는다. 앱의 빌드 메뉴가 명세를 순서대로 부르고 뿌리 경로를 코드 상수로 넘긴다 — 순서와 의존이 코드에 드러나고, 설정 자산이 하나 줄어든다.

시안 판 크기는 게임마다 다르다(ked 1600×900, 블랙홀 1920×1080). 화면 뿌리를 만들 때 판 사각형을 넘기면, 그 아래 노드는 부모의 시안 사각형을 기준으로 앵커 좌표를 계산한다.

## 화면 묶음

화면 하나를 묶음 하나로 둔다 — 그 화면의 코드 · 프리팹 · 그림 · Presentation이 한 폴더에 있다.

```text
<UI 뿌리>/
├─ <런타임 asmdef>             뿌리에 둔다(Common · Screens를 덮는다)
├─ Common/                      여러 화면이 같이 쓰는 것 — 어느 화면도 이름으로 알지 않는다
│   ├─ Scripts/                 부품 키트(버튼 · 슬라이더 …)
│   ├─ Editor/                  키트로 짓는 도구 · 묶음 설정 + 에디터 asmdef(UIPresentationFlow.Editor를 참조)
│   ├─ Sprites/                 둘 이상의 화면이 쓰는 그림
│   └─ Fonts/
├─ Screens/<묶음>/
│   ├─ Scripts/                 화면 · 위젯 스크립트(UIBase<TRefs>)
│   ├─ Prefabs/                 산출물
│   ├─ Presentation/            <화면 키>Presentation.asset
│   ├─ Sprites/                 그 화면만 쓰는 그림(없으면 폴더도 없다)
│   └─ Editor/                  빌드 명세 + 에디터 asmdef를 가리키는 .asmref
└─ App/                         화면을 쓰는 앱 — 제 asmdef 한 쌍(런타임 · 에디터)
    ├─ Runtime/                 화면 흐름 · 호스트(어느 화면을 언제 여는지), 게임 런타임에 잇는 것
    └─ Editor/                  화면 목록 · 캔버스를 짓는 앱 빌드
```

- Page는 주인 Panel의 묶음에 둔다. 명세 하나가 여러 화면을 만들면(확인 · 안내 창) 한 묶음에 둔다.
- 화면 흐름, 앱 설정 값, 화면을 모은 캔버스, 글자 표(CSV 하나)는 묶음에 넣지 않는다. 화면을 쓰는 앱의 몫이다.
- **게임 런타임에 매인 것은 앱에만 둔다.** 런타임 형식을 받는 항목 프리팹, 런타임 계약을 구현하는 어댑터, 런타임 형식의 데이터 — 묶음의 화면은 UI 부품(대사창 · 선택지 상자의 그리기)만 내놓고, 앱이 그 위에 계약을 잇는다. 코드는 묶음 asmdef가 이 프레임워크와 Unity 패키지만 참조해서, 에셋은 묶음 감사(`UIScreenUnits.Audit`)가 바깥을 가리키는 GUID를 찾아서 막는다.
- **묶음은 옮겨도 돈다.** 뿌리를 고정 경로로 쓰지 않고 런타임 asmdef가 있는 폴더로 찾는다(이 프레임워크 코드의 자리도 asmdef로). 그래서 `Common` · `Screens`만 다른 저장소로 복사하면, 그 저장소의 앱이 같은 명세로 그 저장소의 Unity에서 다시 짓는다 — 이 저장소의 비주얼 노벨 샘플이 그렇게 들였다(아래 "참고 구현").
- **옮겨 다니는 묶음은 화면 키를 고정한다.** 화면 키(`UIViewKey`, 기본은 타입 짧은 이름)는 프로젝트에서 하나여야 한다. `TitleScreen` · `SettingsPanel` 같은 이름은 들이는 프로젝트에도 흔하다 — ked 묶음을 이 저장소에 들이자 블랙홀 데모와 셋이 겹쳤다. 묶음의 화면 · 위젯마다 `[UIViewKey("<접두사>.<타입>")]`을 붙이고, Presentation 파일 이름 · `presentationId`도 그 키를 따른다. 앱의 검사가 접두사와 `presentationId` = 키를 본다(ked `KedUIValidate`).
- **asmdef 아래의 `Editor` 폴더는 에디터 전용이 아니다.** 런타임 asmdef가 뿌리에 있으면 묶음 안의 `Editor/`도 그 아래라, `.asmref`로 에디터 asmdef에 붙여야 한다. 실행 쪽과 짝이 맞는다: `Common/Scripts` ↔ `Common/Editor`, `Screens/X/Scripts` ↔ `Screens/X/Editor`, `App/Runtime` ↔ `App/Editor`(앱은 제 asmdef 한 쌍).
- 그림은 경로가 아니라 이름으로 찾게 하면, 공용과 화면 전용 사이를 옮겨도 명세를 고치지 않는다. 같은 이름은 둘 두지 않는다.

## 특수 화면 — 프리팹을 직접 만들 때

비정형 배치나 복잡한 연출처럼 명세로 나타내기 어려운 화면은, 프리팹을 손이나 에디터 스크립트로 직접 만들어도 된다. 조건은 셋이다.

1. 같은 `UIBase<TRefs>`를 쓴다. 게임과 잇는 방식은 하나로 남는다.
2. 묶음 구조를 따른다.
3. 같은 검사를 지난다.

모든 화면을 명세로 덮으려고 명세를 넓히지 않는다. 데이터로 화면을 조립하던 구조에서 프리팹 중심으로 돌아온 까닭이 그것이다. 명세를 넓힐지, 공용으로 올릴지는 사람이 정한다.

## 검사

빌드와 따로 돌 수 있어야 한다. 그래야 손으로 만든 프리팹도 같은 그물을 지난다. 메뉴 `Tools/UI Presentation/Validate Screens`는 프로젝트 전체를 보고, 앱은 `UIScreenValidation.Run`에 자기 폴더와 엄한 검사를 골라 넘긴다.

- **Refs** — 화면 · 위젯마다 `Refs`의 이름이 제 아래에 몇 개인가(`UIBase`는 이름으로 첫 번째를 잡는다). 둘 이상이면 문제. 없으면 등록하는 화면(Root · Panel · Page · Overlay)은 문제고, 위젯은 일부만 쓸 수 있어(한 프리팹, 여러 꼴) 기본으로는 넘어간다 — 앱이 엄하게 볼 수 있다.
- **Presentation** — 오브젝트 이름이 파일 이름과 같다. `presentationId`가 비면 `UIContext.PresentationOverrides`로 Variant를 고를 수 없을 뿐 틀린 것은 아니라, 앱이 고른다(ked는 화면 키를 id로 쓰므로 엄하게).
- **그림 이름** — 같은 이름이 둘 없다(그림을 이름으로 찾는 앱).
- **묶음이 닫혀 있다** — 묶음 안의 에셋이 가리키는 것이 제 묶음 · Common · 이 프레임워크 · 게임 쪽 프레임워크 · Unity 패키지뿐이다. 다른 화면 묶음을 가리키지 않는다.

배치 모드 진입점(`-executeMethod`)을 두면 사람이 메뉴를 누르지 않아도 빌드 · 검사를 돌릴 수 있다. Unity가 그 프로젝트를 열고 있으면 배치 모드는 프로젝트를 열지 못한다.

## 배포(반입) — 두 방식

묶음은 원본과 산출물(`.meta` 포함)을 함께 담는다.

| 받는 쪽 | 방법 |
|---|---|
| Unity 버전 · 패키지가 같다 | 산출물째 들인다 — 검수한 그대로, GUID 그대로 |
| 다르다 | 원본과 산출물의 `.meta`를 들이고 그 자리 위에 다시 빌드한다 — 직렬화 형식 문제를 피하고 GUID는 지킨다 |

다시 빌드할 때 파일 안쪽 fileID가 Unity 버전을 넘어 그대로인지는 아직 확인하지 않았다.

## 재생성

같은 명세로 다시 빌드하면 산출물의 내용이 같다. 다만 파일이 바이트까지 같지는 않을 수 있다.

- **이름이 겹치는 오브젝트** — 빌더가 지은 프리팹을 다시 지으면, 이름이 하나뿐인 오브젝트의 fileID는 그대로이고 같은 이름이 여럿인 것(ked 저장/불러오기의 슬롯 카드 여섯 장 — `CardButton` 등이 여섯 개)은 매번 바뀐다(ked에서 편집 모드로 두 번 지어 본 결과). 내용과 GUID는 같으므로, 다른 에셋이 프리팹 안쪽 오브젝트를 fileID로 가리키게 두지 않는다(캔버스의 중첩 프리팹 덮어쓰기는 캔버스도 빌드가 다시 만든다).
- **손 프리팹을 처음 명세로 다시 지을 때** — 파일 안 fileID가 모두 새로 매겨진다(블랙홀 일시 정지 창). 그래서 git diff로는 무엇이 달라졌는지 보이지 않는다. 오브젝트는 이름 경로로, 컴포넌트는 종류로 짝지어 fileID를 뺀 값끼리 비교한다. 일시 정지 창은 그렇게 비교해 구조가 같았고, 값은 셋만 달랐다 — 레이어(Default → UI), 쓰지 않는 Selected 색(Sprite Swap 버튼이라 색 전환을 쓰지 않는다), TMP가 그릴 때 다시 채우는 칸(`m_Color` · `m_fontColor32` · 글자 스타일 해시).
- **플레이 중 빌드** — 위 "원본과 산출물". ked의 처음 관찰("여러 번 빌드해도 git 변경 0")은 플레이 중에 돈 빌드끼리였던 것으로 보인다(커밋된 프리팹에 실행 중에만 붙는 `UI_EventHandler`가 있었다). 편집 모드로 두 번 지으니 슬롯 카드가 있는 프리팹만 서로 달랐고 나머지는 같았다(2026-10-27).

## 사람의 역할

1. **만들기 전** — 요구와 품질 기준을 정한다(무엇을 보여 주나, 어떤 입력 · 해상도 · 언어를 견디나).
2. **만드는 동안** — AI의 설계 판단을 정한다: 명세를 넓힐지, 공용으로 올릴지, 특수 화면으로 뺄지.
3. **만든 뒤** — Unity에서 눈으로 검수하고 승인한다(보기 · 조작 · 화면비 · 다국어 · 실제 흐름). 문제를 찾으면 프리팹이 아니라 원본을 고쳐 다시 빌드한다.

자동 검사는 참조와 구조를 거른다. 화면이 보기 좋은지, 조작하기 편한지, 의도한 분위기인지는 사람이 판정한다.

## 참고 구현

**ked-presentation-runtime** `Assets/Samples/KedUI` — 12화면, 화면 묶음 구조:

- `Common/Editor` — 부품 키트(`KedUIKit` — KedUI의 그림 · 글꼴 · 버튼 꼴), 묶음 설정(`KedUIUnits` — 뿌리 · 허용한 곳), 검사 메뉴(`KedUIValidate` — 이 프레임워크의 검사를 엄하게 + 묶음 감사 + 그림 이름), 글꼴(`KedUIFonts`)
- `Screens/*/Editor` — 화면 빌드 명세 8개
- `App/` — 재생 런타임에 잇는 앱: 흐름 · 호스트, 대사창 · 선택지 상자의 런타임 계약 어댑터, 선택지 항목(본체 형식), 연출 배치 DB, 글자 표. 화면 목록과 캔버스를 짓는 앱 빌드(`App/Editor/KedUIBuild`)

**이 저장소의 비주얼 노벨 샘플** `Assets/Demo/VisualNovel` — 위 묶음(`Common` · `Screens`)의 복사본과 이 저장소의 앱:

- `KedUI/` — 복사본. 명세 · 키트 · 그림은 여기서 고치지 않는다(ked에서 고쳐 다시 들인다 — `Documentation~/vendoring.md`). 프리팹 · 글꼴 SDF는 이 저장소의 Unity로 다시 짓는 산출물이다
- `App/Editor/VNDemoBuild` — 메뉴 `UI Demo/Build Visual Novel Demo`. 묶음의 명세를 ked 앱 빌드와 같은 순서로 불러 짓고, 캔버스 대신 씬을 만든다. 선택지 항목은 데모 형식(`VNDemoOptionItemSpec`)
- `App/Runtime` — 재생 런타임 대신 가짜 재생(`VNDemoPlayer` — 대본 · 타자기 · 자동 · 빨리 넘기기 · 되감기)과 메모리 저장. 흐름(`VNDemoFlow`)은 ked의 흐름과 같은 자리다

**이 저장소의 블랙홀 데모** `Assets/Demo/BlackHole` — 묶음 구조가 아닌 폴더에서 같은 도구를 쓴다:

- `Editor/BlackHoleScreenKit` — 블랙홀의 부품 꼴(Sprite Swap 그림 버튼, 먹색 글자). 그림은 `Art/GUI`에서 이름으로 찾되 `Dark/`(같은 이름의 어두운 판)는 뺀다
- `Editor/Screens/PausePanelSpec` — 게임의 손 프리팹을 명세로 옮긴 것. 시안 판 1920×1080
- `Editor/BlackHoleScreenBuild` — 메뉴 `UI Demo/Build BlackHole Screens`(지금은 일시 정지 창 하나)

옮겨 온 경위와 남은 일은 [PLAN_from-ked](PLAN_from-ked.md)의 B, 비주얼 노벨 샘플은 [PLAN_vn-sample](PLAN_vn-sample.md).
